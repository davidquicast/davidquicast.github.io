# Static portfolio capabilities

The site stays on Jekyll and GitHub Pages. Ruby builds and validates content; HTML/CSS and small native JavaScript controllers provide the public interface. There is no registration, user database or publishing backend. Content and credentials belong in different places: profile identifiers and public service IDs may be configured; API tokens and private keys must never enter source or client HTML.

## Profile and catalog composition

`_layouts/about.liquid` renders a persistent profile sidebar and one shared catalog. The default All view contains every public record; Projects, Blogs and Research filter the same data. Work/About navigation remains the same on home and detail pages. `_plugins/profile-feed.rb` generates its records from genuine projects, public posts and `_data/publications.yml`. Every record has a content type, search text, stable rank and internal sorting timestamp. Projects and papers with year-only metadata retain year precision; no exact publication day is presented. An explicit ISO 8601 `published_at` can supply a real timestamp. New public articles enter the catalog without manual slug maintenance.

`_data/profile_feed.yml` defines `featured_projects` in author-selected order and `spotlight_projects` in preview order. Recommended All ordering gives selected records priority: current projects follow spotlight order, then other selected projects follow their author-defined order, with stable type interleaving. Remaining work follows importance and URL; Newest/Oldest use real timestamp or year precision. Current-work entries are ordinary project cards and are never duplicated as a preview deck. Missing spotlight identifiers are ignored, repeated entries are deduplicated and an empty selection creates no spotlight. Spotlight search and sorting metadata come from the actual selected projects. Selection is displayed as a mark within All, rather than an extra category. All, Projects, Blogs and Research use the same underlying records. Sorts and search update the URL, and browser history restores the view.

Both page `latest_posts` and global `latest_posts.enabled` gate writing. `latest_posts.limit` marks recent articles; it does not truncate All/Blogs. Negative limits mark all public writing. An article explicitly marked `featured: true` remains selected independently of that recent-article limit. `latest_posts.scrollable: true` adds a named, keyboard-focusable scroll region only in the Blogs view, without nested copies of cards. Home `selected_papers` controls whether records marked `selected: true` receive a mark within All; the complete genuine publication dataset remains accessible through Research and `/publications/`.

`assets/js/profile-feed.js` measures card heights after width and text composition settle, places each card in the shortest column and animates changed positions with native Web Animations. ResizeObserver updates the layout after content, fonts or widths change. Animation handles are canceled when superseded, on reduced motion and when the document is hidden. DOM order follows the selected sorting order. CSS provides a readable fallback, and native project/blog/publication links remain available without JavaScript.

`assets/css/wall.css` owns the catalog canvas and card presentation. `assets/js/card-menu.js` enhances the actual image and copy-link actions declared by `card-actions.liquid`. The full biography at `/about/`, sourced from `_pages/en-us/profile.md`, reuses owner content and profile information from `_pages/en-us/about.md`. Home image filename/URL, shape, alignment and extra information remain configurable. `social` controls real connections in the persistent sidebar; the About reader keeps biography and CV actions together. Platform icons are local SVGs or the official locally served Hugging Face color logo. Visible connection text is the actual username or email; platform names remain in accessible labels and tooltips. Custom logos use validated HTTPS or existing local asset paths. There are no simulated social counts or publishing controls.

## Connections and project destinations

`_data/socials.yml` continues to accept every original template profile key. Usernames such as `github_username`, `linkedin_username`, `x_username` and `huggingface_id` display as `@username`; email displays the actual address. Known custom profile URLs can supply a single genuine handle, while resource paths such as a Hugging Face Space do not fabricate a profile username. `custom_social` accepts either one object or a list, with `title` or `label`, `url`, optional `handle`/`username` and optional `logo`. An unknown site without an explicit handle keeps its author-provided title. Unsafe URLs and custom image paths are rejected.

For example, a future custom connection can use:

```yaml
custom_social:
  - label: Research network
    username: your-handle
    url: https://example.org/your-profile
    logo: /assets/img/your-logo.svg
```

`profile-links.liquid` renders actual handles/email and keeps each platform in its accessible name and tooltip. `brand-icon.liquid colored=true` opts into the pinned official palette; other contexts retain inherited color. GitHub and X use theme-aware monochrome; LinkedIn uses its brand blue. The official multicolor Hugging Face SVG is served once locally and retained unchanged. Source, usage and license details are public in `assets/brand-icons-NOTICE.txt`.

`ProjectDestinationsGenerator` reads actual `github`, `huggingface`, `redirect` and `project_items[*].url` values. It retains only exact GitHub/Hugging Face hosts, rejects unsafe schemes, credentials and nonstandard ports, and deduplicates equivalent authored resource paths. `_includes/project-destinations.liquid` emits compact platform actions for `context='card'` and resource-specific labels for `context='detail'`. It omits empty controls and preserves each first authored URL instead of synthesizing a repository or model address.

## Optional content loading

`_includes/optional-features.liquid` emits an inert JSON configuration and one controller only on pages requesting capabilities. The controller fetches a library only when the matching content exists. Ordinary pages do not receive a jQuery/chart/map bundle. Shared resources are loaded once, failures preserve the source, and rendering success moves the source into a native “View source” disclosure.

Library versions and SRI values remain centralized in `_config.yml`. `python3 tools/verify-optional-resources.py` checks the 24 resources consumed by the optional loader. The current audit found and corrected two historical CSS hash mismatches (Leaflet and image comparison). All 24 then returned HTTP 200 and matched configured integrity values. This is a network/integrity verification, not an assertion that every external account or every possible visualization configuration was exercised.

When writing an optional diagram or chart, use the matching frontmatter flag and original fenced-code language. Supply real data and a useful caption/description. Authored source remains available when scripting, networking or a third-party library fails. Configure only the visualization engine required for the article. Native image zoom replaces overlapping legacy image libraries, retaining their familiar markup hooks.

## Multilingual readiness

English remains the sole public locale. `show_language_switcher` is false. Existing inactive Portuguese sources are preserved and excluded; many are theme examples and must not be published as the author's translations.

To activate a reviewed locale later:

1. Add genuine localized pages/posts/projects with the same `page_id` as their equivalents. `permalink` may differ; Polyglot links matching translations.
2. Add `_data/<locale>/ui.yml` and, when needed, `strings.yml` month names. Missing UI keys fall back to English. Existing content fallback keeps its actual source language in HTML/metadata.
3. Add the locale to `languages`, remove its source paths from `exclude` only after replacing examples, and enable `show_language_switcher` when public switching is wanted.
4. Build into an isolated output and verify canonical, hreflang, navigation, dates, search and fallback routes before publishing.

Templates use `ui_label`, `content_locale`, `locale_tag`, `og_locale`, `locale_url` and `localized_date`. Browser controllers read safely escaped inert JSON from `#portfolio-ui`. Date patterns may be supplied as `ui.date.long`, `short` or `month_year`, using `{month}`, `{day}` and `{year}`. Navigation/profile identities and article content stay in their own content data rather than being invented by a translator.

`bundle exec ruby scripts/verify-capabilities.rb` builds a private two-locale fixture under `.local`, exercises different translated permalinks, correct canonical/hreflang, locale-preserving internal links and search, fallback source language, escaped dictionary merging and dates. Its 15 contracts also check real publication rendering, valid downloadable BibTeX, native tabs, optional feature manifests, opt-in schema and DOI badge markup. Real shared templates are rendered against regenerated catalog data for each writing/selection variant, alongside related-post, navbar-social, project-category and image-zoom settings. The checks assert the complete Blogs catalog, selected-record limits and marks, paper selection, persistent sidebar connections, image variants, truthful All counts, the four categories, universal Work/About navigation and genuine contextual project destinations. Fixture authors and papers never enter production.

## Dynamic article capability lifecycle

The local optional-feature dispatcher is installed on every page, including profiles with no optional manifest. It loads no visualization SDK until an enabled feature has matching content. A fetched same-origin overlay passes a bounded inert feature manifest to `portfolio:content-mounted`; the dispatcher accepts known feature identifiers and HTTPS or same-origin resource URLs. Scripts from fetched HTML are never imported. The shared SDK promise cache has a hard limit of 64 distinct resources and retries failed loads. Duplicate mounts are ignored. A dispatcher loaded after the reader has opened adopts its already-mounted manifest.

Closing a reader aborts scoped listeners and newsletter requests, disconnects resize/theme observers, destroys Chart.js/ECharts/Leaflet/Masonry instances, finalizes Vega views, tears down enhanced tables and restores native source/tab markup. Pending SDK responses may populate the shared SDK cache but cannot render into a closed scope. MathJax uses scoped `typesetPromise` and `typesetClear`, with global startup typesetting disabled. Code-source restoration cooperates with the code-copy controller's independent teardown.

Video/iframe markup uses a native scoped dialog because the pinned VenoBox 2.1.8 SDK has no destroy API and adds an anonymous body keyup listener on each opening. Ordinary YouTube/Vimeo URLs are converted to their official embed URLs; direct MP4/WebM/OGG/M4V links use a native video element. The dialog retains an original-media link, validates URLs, restores trigger focus, and consumes its own Escape key. External providers may reject embedding; the original link stays usable.

TikZJax v1 only exposes a `window.onload` scan. A normally loaded static page retains that integration; an already-loaded dynamic reader keeps text/copyable TikZ source and a canonical full-page link instead of claiming an unsupported rescan API. Giscus/Disqus and metric badges still require valid provider configuration and network access. Disqus owns one global thread: a second concurrent owner receives a full-page comments link. The provider account, badge data and externally hosted rendering APIs have not been exercised against real accounts. The six current public articles do not enable these provider features.

`tests/optional-features.spec.js` adds twenty scoped chart/tab reuse cycles, delayed SDK completion after unmount, map/ECharts observer destruction, late dispatcher adoption and native media Escape/focus coverage to the existing source/error/security/newsletter contracts. All provider responses in these fixtures are mocked; no real subscription or paid service is used.

The original CV PDF also has deterministic responsive page previews and selectable extracted text, generated during normal build/watch. See [CV maintenance](cv.md) for source integrity, tools, budgets and regeneration.
