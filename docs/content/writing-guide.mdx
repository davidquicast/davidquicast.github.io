Esta guía es **vinculante** para cualquier post académico o editorial de largo formato publicado en `_posts/en-us/`. Para posts introductorios, la guía es referencia recomendada pero no obligatoria.

Lee esto antes de redactar una sola línea. Si la pieza no puede cumplir estos criterios, no se publica como tier académico.

---

## Principios

1. **Investigación real, no fabricación.** Todo claim no trivial debe estar respaldado por una fuente verificable. No inventar autores, papers, DOI ni enlaces. Si no puedes verificar una fuente, no la uses.
2. **Densidad sin padding.** Cada párrafo debe avanzar el argumento. Eliminar oraciones que sólo introducen lo que vas a decir o resumen lo que acabas de decir.
3. **Conexión con Personaxis sin invasión.** Puedes referenciar Personaxis, `persona.md`, o decisiones de diseño del producto cuando el argumento lo pida. **No documentes código del CLI ni campos exactos del spec en el blog**: ambos están en cambio continuo y el contenido se vuelve stale. Trata la spec como inspiración conceptual.
4. **Sin claims metafísicas no respaldadas.** Nunca afirmar que el agente "tiene conciencia", "siente", "experimenta". Usar siempre framing funcional: "estados funcionales", "monitoreo arquitectónico", "patrones de comportamiento".
5. **Evita los tells de IA generativa.** Ver [sección dedicada](#patrones-de-ia-a-evitar) abajo. Esta es la diferencia entre un post que se siente humano y uno que el lector descarta a la tercera oración.

## Estructura canónica de un post académico

```
1. Apertura provocadora (1-2 párrafos)
   ↳ Un problema concreto y reconocible para el lector.
   ↳ Una afirmación que desafía la intuición común.

2. Tesis explícita (1 párrafo)
   ↳ Qué argumenta el post y por qué importa.

3. Fundamentación teórica (3-5 secciones)
   ↳ Las fuentes académicas relevantes.
   ↳ Cada teoría introducida con autor + año + claim central.
   ↳ Citación numérica al final de cada claim derivado.

4. Aplicación al dominio de agentes IA
   ↳ Cómo la teoría se traduce en arquitectura.
   ↳ Referencia a las 10 capas de Personaxis sin profundizar en código.

5. Implicación práctica (1-2 secciones)
   ↳ Qué pasa si se ignora.
   ↳ Qué arquitectura emerge cuando se toma en serio.

6. Conclusión (1-2 párrafos)
   ↳ Recapitular sin repetir.
   ↳ Cerrar con una frase que sostenga la tesis del inicio.

7. Referencias
   ↳ Numéricas, con enlaces verificables.
```

Longitud típica: 2.500 a 3.500 palabras. Más corto se siente superficial; más largo cansa.

## Frontmatter requerido para esta repo

```yaml
---
layout: post
title: "Título descriptivo y específico (no clickbait)"
date: 2026-MM-DD 09:00:00 -0500
description: "Una oración que captura la tesis. Entre 140 y 220 caracteres."
tags: [tag-1, tag-2, tag-3]
categories: [notes]
featured: false
image: assets/img/blog/YYYY-MM-DD-slug_1.png
---
```

Reglas:

- `title`: específico y argumentativo. Bien: _"Personhood Without Consciousness: The Case for Functional Identity in AI Agents"_. Mal: _"Why Persona Design Matters"_.
- `date`: ISO `YYYY-MM-DD`. Posterior al último post publicado.
- `image`: debe apuntar a un PNG real en `assets/img/blog/` y seguir `docs/blogs/image-generation-rules.md`.
- `description`: la apertura provocadora condensada. Visible en cards de listado.
- `tags`: 3-5 tags. Mezclar disciplina (`philosophy-of-mind`, `cognitive-science`) y dominio (`ai-agents`, `persona-design`).

## Sistema de citación

### En el cuerpo del texto

```mdx
La identidad personal no puede reducirse únicamente a continuidad factual,
porque también depende de patrones narrativos y disposiciones afectivas [[1]](#ref-1).
```

Cuando una oración usa varias fuentes, encadenar:

```mdx
Tulving [[3]](#ref-3) introdujo la distinción episódica-semántica;
Conway [[5]](#ref-5) extendió esto al sistema autobiográfico.
```

### Sección de referencias

```mdx
## References

<a id="ref-1"></a>
**[1]** Locke, J. (1975). *An Essay Concerning Human Understanding*.
Oxford: Clarendon Press. (Original work published 1689.)
[Project Gutenberg edition](https://www.gutenberg.org/ebooks/10615)

<a id="ref-2"></a>
**[2]** Parfit, D. (1984). *Reasons and Persons*. Oxford: Oxford University Press.
[DOI: 10.1093/019824908X.001.0001](https://doi.org/10.1093/019824908X.001.0001)
```

### Reglas de enlaces verificables

Orden de preferencia:

1. **DOI canónico** (`https://doi.org/...`).
2. **Página del editor** (MIT Press, Oxford Academic, Cambridge, Springer).
3. **Archivo abierto verificable** (Frontiers, PMC, PhilPapers, repositorios institucionales).
4. **Project Gutenberg / SEP** para clásicos de dominio público.
5. **WorldCat** como último recurso para libros antiguos sin presencia digital del editor.

Nunca enlazar a:

- Sci-Hub ni copias piratas.
- Resúmenes de blog secundarios como fuente primaria.
- Wikipedia como cita académica (puede usarse para definiciones en `<KeyConcept>`, no como fuente).

## Uso de componentes

Esta repo usa posts Jekyll Markdown (`.md`) en `_posts/en-us/`. No asumir soporte MDX ni importar componentes React/MDX en un post salvo que el sitio se haya migrado explícitamente.

Regla de oro: **un elemento visual sólo se usa si aporta valor pedagógico real**. No decoración. Por post académico:

- 1 imagen hero generada según `docs/blogs/`.
- 1 cita textual breve de un autor citado, si aporta al argumento.
- 1-2 definiciones breves en prosa para términos que el lector necesita anclar.

Más es ruido. Si una sección no necesita visual, no la fuerces.

## Patrones de IA a evitar

Aplica esta lista local como regla editorial: palabras prohibidas (delve, leverage, robust, tapestry, realm, landscape, etc.), patrones sintácticos prohibidos (em dash, "not X, but Y", triadas, aperturas cliché, meta-commentary), capitalización inflada y cierres tipo CTA.

### Adiciones específicas para el tier académico

Los siguientes patrones son particulares de prosa argumentativa larga y no están explícitamente en `ai-tells.md`:

| Patrón | Por qué falla en blog académico | Sustituir por |
| --- | --- | --- |
| **Aposición en cada nombre propio** ("Frankfurt, the influential philosopher, argued...") | Cliché de divulgación; trata al lector como ignorante | "Frankfurt argued..." y dejar que la cita lo identifique |
| **Adverbios de intensidad** (truly, really, incredibly, remarkably, fundamentally) | Reemplazo de argumentación por énfasis verbal | Eliminar; si la afirmación necesita el adverbio, falta evidencia |
| **Hedge + claim** ("It could be argued that personhood is constitutive of...") | Postergar el compromiso debilita el argumento | Afirmación directa o cita explícita del autor que hedge |
| **Rule of three en oración corta** ("The agent thinks, feels, and responds") | Patrón retórico sobreajustado del RLHF | Listas de 2, 4 o prosa |
| **Restatement de la tesis en la conclusión** | Asume que el lector no recordó | Sostener la tesis con una frase nueva que la implica |
| **"As we've seen..." / "As discussed above..."** | Meta-referencia al texto mismo | Pasar al siguiente argumento sin anunciar la transición |
| **"In this post, I will argue..."** | Anuncio de intenciones; mata el ritmo | Empezar el argumento directamente |

### Test del lector escéptico

Antes de publicar, lee el post completo preguntándote: **¿qué fracción de las oraciones podría aparecer idéntica en cualquier otro blog tech?** Si la respuesta es más del 20%, el post carece de voz propia y necesita reescritura.

### Pre-ship grep adicional para blog académico

Sumar al grep documentado en `marketing/ai-tells.md`:

```
truly
incredibly
remarkably
fundamentally
arguably
it could be argued
as we've seen
as discussed
in this post
as mentioned
in this article
let me argue
let us examine
```

Si cualquiera de estos aparece, reescribir antes de mergear.

## Reglas de lenguaje general

- **Inglés** como locale canónico (`.en.mdx`).
- **No primera persona del autor** ("I argue", "I think") salvo cuando es genuinamente personal. La voz argumentativa directa es más fuerte: "The argument is", "On this view".
- **No marketing.** Prohibido: _"revolutionary", "game-changing", "powerful", "robust", "best-in-class"_. Si una afirmación necesita un adjetivo así, probablemente no está demostrada.
- **No teaser endings.** Prohibido cerrar con "_to learn more, browse the registry_". Si el lector llegó al final, mereció un cierre, no un CTA.

## Checklist antes de publicar

```
[ ] Frontmatter completo y schema válido (date posterior al último post).
[ ] Tesis explícita en los primeros 3 párrafos.
[ ] Todas las fuentes verificadas contra DOI / publisher / archivo abierto.
[ ] Citación numérica con anclas internas (`[[N]](#ref-N)`).
[ ] Sección References con enlaces clicables a cada fuente.
[ ] Cero em dashes (—).
[ ] Cero patrones "It's not X, it's Y" / "Not X. Y."
[ ] Cero palabras de la lista E (delve, tapestry, realm, robust, etc.).
[ ] Cero aperturas/cierres de la lista B / F.
[ ] Headers solo donde cambia el argumento.
[ ] Sin claims metafísicas ("sentir", "conciencia subjetiva").
[ ] Sin código del CLI ni campos exactos del spec.
[ ] 1 visualización conceptual + Pullquote + KeyConcept si aportan valor.
[ ] Validación estática de frontmatter y rutas de imagen.
[ ] No correr Docker desde Codex; el usuario valida el servidor local.
```

## Anti-patrones específicos del proyecto

| Anti-patrón | Por qué falla |
| --- | --- |
| Citar a un autor sin DOI ni enlace verificable | El lector no puede comprobar; erosiona confianza |
| Usar `font-mono` para párrafos largos | Viola DESIGN.md §10.2; ilegible |
| Hacer marketing del producto al final | El blog ya legitima el producto por su rigor; el CTA sobra |
| Documentar código del CLI o spec | Se vuelve stale en semanas |
| Listar 10 conceptos sin argumento que los hile | Listicles son otro género, no académico |
| Pullquote con frase del autor del post | Es un altavoz, no una autoridad citable |
| Reusar la misma visualización en dos posts | Cada `<Visual />` es para un argumento específico |
